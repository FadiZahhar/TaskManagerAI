ID	User Story	Acceptance Criteria	Notes / Edge Cases
US-001	As an API client, I want to create a task so that I can track work items in the Task Tracker API.	Given a valid task payload with title, description, status, priority, and assignee, when I send POST /tasks, then the API returns 201 Created with the created task.The response includes a generated id.The response includes the submitted title, description, status, priority, and assignee.The generated id is unique across tasks.	Valid status values are only ToDo, InProgress, and Done.Valid priority values are only Low, Medium, and High.The client should not provide id when creating a task; if provided, the API should ignore it or reject it consistently.
US-002	As an API client, I want invalid task creation requests to be rejected so that only usable task data is stored.	Given a create request with a missing required field, when I send POST /tasks, then the API returns a validation error, preferably 422 Unprocessable Entity.Given a blank or whitespace-only title, when I send POST /tasks, then the API returns a validation error.Given an invalid status, when I send POST /tasks, then the API returns a validation error.Given an invalid priority, when I send POST /tasks, then the API returns a validation error.	Required fields: title, description, status, priority, and assignee.Examples of invalid status: todo, In Progress, Blocked, Complete.Examples of invalid priority: low, Urgent, Critical, Normal.This story keeps validation simple and API-focused.
US-003	As an API client, I want to view a list of tasks so that I can see all tracked work items.	Given tasks exist, when I send GET /tasks, then the API returns 200 OK with a list of tasks.Each task in the response includes id, title, description, status, priority, and assignee.Given no tasks exist, when I send GET /tasks, then the API returns 200 OK with an empty list.	The response should be deterministic enough for tests, such as returning tasks in creation order or by id.No pagination is required for this small learning project unless added in a later module.
US-004	As an API client, I want to view a single task by ID so that I can inspect one work item.	Given a task exists, when I send GET /tasks/{id}, then the API returns 200 OK with that task.The returned task includes id, title, description, status, priority, and assignee.Given no task exists for the requested id, when I send GET /tasks/{id}, then the API returns 404 Not Found.	Missing task behavior must be consistent across the API.The error response should be simple and testable, for example: {"detail": "Task not found"}.Invalid ID formats should return a validation error if the route expects a typed ID.
US-005	As an API client, I want to update a task so that I can correct or revise task details.	Given a task exists, when I send PUT /tasks/{id} or PATCH /tasks/{id} with valid updated fields, then the API returns 200 OK with the updated task.The API persists the updated title, description, status, priority, and assignee values according to the chosen update style.Given no task exists for the requested id, when I send an update request, then the API returns 404 Not Found.Given invalid updated data, the API returns a validation error and does not update the task.	Choose either full replacement with PUT or partial update with PATCH before implementation; avoid implementing both unless the course requires it.Validation edge cases should match create-task validation.id should not be editable.
US-006	As an API client, I want to delete a task so that removed work items no longer appear in the tracker.	Given a task exists, when I send DELETE /tasks/{id}, then the API returns 204 No Content or 200 OK with a simple confirmation.After deletion, GET /tasks/{id} returns 404 Not Found.After deletion, the task no longer appears in GET /tasks.Given no task exists for the requested id, when I send DELETE /tasks/{id}, then the API returns 404 Not Found.	Prefer 204 No Content for a simple REST-style delete response.Deleting a missing task should not silently succeed unless that behavior is intentionally documented.
US-007	As an API client, I want to filter tasks by status and priority so that I can find relevant work items.	Given tasks with different statuses exist, when I send GET /tasks?status=ToDo, then the API returns only tasks with status equal to ToDo.Given tasks with different priorities exist, when I send GET /tasks?priority=High, then the API returns only tasks with priority equal to High.Given both filters are supplied, when I send GET /tasks?status=InProgress&priority=Medium, then the API returns only tasks matching both filters.Given no tasks match the filters, the API returns 200 OK with an empty list.	Invalid status filter values should return a validation error.Invalid priority filter values should return a validation error.Filters should use exact enum values: ToDo, InProgress, Done, Low, Medium, High.
US-008	As an API client, I want task status movement rules to be enforced so that completed work cannot be reopened accidentally.	Given a task is ToDo, when I update its status to InProgress, then the API accepts the change.Given a task is InProgress, when I update its status to Done, then the API accepts the change.Given a task is ToDo, when I update its status directly to Done, then the API accepts the change unless stricter workflow rules are later added.Given a task is Done, when I try to update its status to ToDo or InProgress, then the API rejects the request with a clear error, such as 400 Bad Request.Given no task exists for the requested id, status movement returns 404 Not Found.	The key workflow rule is: a task in Done cannot move back to ToDo or InProgress.Invalid status values should still return validation errors.This can be tested through the normal update endpoint or a dedicated status movement endpoint, but the project should choose one approach before implementation.
