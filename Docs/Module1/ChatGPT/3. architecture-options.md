2. Recommended option

Recommend Option 1: FastAPI with in-memory storage as the Module 1 architecture direction.

For the current Module 1 deliverable, I would keep the actual implementation even smaller: FastAPI app skeleton only, with GET /health, Swagger docs at /docs, and no task storage code yet. The ADR can state that when task CRUD begins, the first implementation will use an in-memory repository to keep the learning focus on API contracts, validation, routing, status transitions, and tests.

This is the best fit because Module 1 is about proving the project can run locally and exposing a minimal API surface. Adding JSON file storage or SQLite/SQLModel now would solve problems the project does not yet have. FastAPI already gives you the right foundation for request/response models, validation, and interactive API documentation, so the architecture can evolve without introducing persistence prematurely.  

A good Module 1 ADR position would be:

The Task Tracker API will start as a minimal FastAPI application with GET /health and default Swagger documentation at /docs. No task persistence will be implemented in Module 1. When CRUD work begins, the first storage implementation will use an in-memory repository to keep the project simple, locally runnable, and easy to test. The code should keep route logic separate from storage logic so the in-memory repository can later be replaced by SQLite and SQLModel when durable persistence becomes part of the learning scope.

My ranking:

Rank	Option	Why
1	FastAPI with in-memory storage	Best for Module 1 and early CRUD learning. Lowest friction, easiest tests, least distraction.
2	FastAPI with SQLite and SQLModel	Best next step once persistence becomes a real requirement. Good evolution path, but premature for the current skeleton.
3	FastAPI with JSON file storage	Acceptable for tiny demos, but it creates awkward file-state problems without teaching clean API or database architecture as well as the other two options.

3. Assumptions rejected

Rejected assumption	Why it is rejected
“Because the final app has tasks, Module 1 needs task storage.”	Module 1 only requires a running skeleton, GET /health, and docs. Adding storage now expands scope without improving the required deliverable.
“CRUD requirements mean we need SQLite immediately.”	CRUD can be designed and tested against an in-memory repository first. SQLite becomes valuable when persistence, relational querying, or realistic data lifecycle behavior becomes part of the module.
“A JSON file is a good middle ground.”	It looks simple, but it introduces file I/O, test cleanup, malformed file handling, write consistency, and persistence confusion. For this project, it is neither as simple as memory nor as instructive as SQLite/SQLModel.
“The project needs production-style infrastructure now.”	Authentication, user accounts, production database setup, deployment, Docker, background workers, and frontend concerns are explicitly outside the current scope.
“The first architecture needs to be final.”	For a learning project, the better architecture is staged: skeleton first, in-memory CRUD second, SQLite/SQLModel later when persistence is a learning objective.
“The route handlers can own all business rules.”	Even in a small project, status transition rules like Done not moving back to ToDo or InProgress should be isolated in a small service or domain function so they are easy to test.

4. Risks to revisit if the project grows

Risk	When to revisit	Likely response
In-memory data disappears on restart.	When users expect tasks to survive app restarts.	Move to SQLite with SQLModel.
Filtering becomes more complex.	When filters expand beyond status and priority, or when sorting/pagination are added.	Use database queries instead of manual list filtering.
Global mutable state causes test leakage.	When CRUD tests start affecting each other.	Add test fixtures that reset the in-memory repository, or use dependency injection to provide a fresh repository per test.
Status transition rules become more complex.	When workflow rules expand beyond Done being terminal.	Move transition logic into a dedicated domain/service layer with focused unit tests.
Manual ID generation becomes fragile.	When concurrent requests, persistence, or database migration become relevant.	Let SQLite/SQLModel manage IDs or centralize ID generation in the repository.
Validation rules grow.	When fields need length limits, optional descriptions, assignee format rules, or stricter enums.	Put validation in Pydantic models and keep business rules outside route handlers.
The API contract stabilizes.	When multiple clients or generated docs matter more.	Add more explicit response models, error response conventions, and OpenAPI metadata.
Persistence becomes part of the learning goals.	When a later module asks for durable task storage.	Promote SQLite + SQLModel as the next architecture option.

Bottom line: keep Module 1 as a minimal FastAPI skeleton. Document in-memory storage as the first planned CRUD storage strategy, but do not implement task persistence until the module actually asks for CRUD. SQLite with SQLModel is the right later upgrade path; JSON file storage is the least attractive option for this project.
