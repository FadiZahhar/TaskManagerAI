# Generic Comments Feature Plan

> This plan is intentionally repository-agnostic. Route examples are illustrative and do not imply knowledge of the application’s actual conventions.

## 1. Data Model

Define a comment entity with:

- `id`: UUID string, generated by the server.
- `task_id`: string identifying the associated task.
- `author`: required string, 1–100 characters.
- `body`: required string, 1–2000 characters.
- `created_at`: server-generated UTC datetime.

Plan separate request and response shapes:

- Create input accepts `author` and `body`; derive `task_id` from the route or request context.
- Response includes all comment fields.
- Clients cannot supply or override `id` or `created_at`.
- Decide whether leading and trailing whitespace is trimmed before length validation.
- Reject blank values after trimming if trimming is adopted.
- Define what happens when the referenced task does not exist.
- Define comment lifecycle when its task is deleted: cascade deletion, rejection of task deletion, or orphan retention.
- If editing is supported later, use a dedicated update shape rather than making creation fields optional prematurely.

## 2. API Routes

Choose a route style consistent with the existing API. A nested design might use:

- `POST /tasks/{task_id}/comments` — create a comment for a task.
- `GET /tasks/{task_id}/comments` — list comments for a task.
- `GET /tasks/{task_id}/comments/{comment_id}` — retrieve one comment.
- `DELETE /tasks/{task_id}/comments/{comment_id}` — delete a comment, if deletion is in scope.

Possible future route:

- `PATCH /tasks/{task_id}/comments/{comment_id}` — edit the author or body, only if comment editing is explicitly required.

Define for each route:

- Request and response schemas.
- Success status codes.
- Validation-error behavior.
- Missing-task and missing-comment behavior.
- Whether a mismatched `task_id` and `comment_id` is treated as not found.
- Comment ordering, such as oldest-first or newest-first.
- Authorization rules for creating, viewing, editing, and deleting comments.
- Whether list responses need pagination, limits, or stable ordering.

At minimum, creating a comment should verify that the referenced task exists and generate `id` and `created_at` on the server.

## 3. Tests

Add tests at the project’s existing testing layers and in its established style.

Cover:

- Creating a valid comment.
- Verifying that the server generates a UUID and UTC timestamp.
- Associating the comment with the requested task.
- Listing comments for a task.
- Ensuring comments from other tasks are excluded.
- Retrieving a specific comment, if that route is included.
- Deleting a comment, if deletion is included.
- Missing-task behavior.
- Missing-comment behavior.
- Mismatched task/comment association behavior.
- Required `author` and `body` validation.
- Minimum and maximum accepted lengths.
- Rejection at 101 author characters and 2001 body characters.
- Empty and whitespace-only values.
- Rejection or handling of unknown input fields, according to existing conventions.
- Deterministic list ordering.
- Task deletion behavior when comments exist.
- Persistence or isolation behavior appropriate to the chosen storage mechanism.
- Authorization and ownership rules, if the application has an identity system.
- Frontend success, validation-error, empty-state, and retry behavior at the appropriate test level.

Use fixed or controlled time only if the project’s testing approach supports it. Avoid tests that depend on wall-clock timing or comment ordering without an explicit ordering contract.

## 4. Frontend Changes

Add a comments area to the task experience using the application’s existing UI patterns.

Potential changes include:

- Displaying comments for the selected task.
- Showing author and creation time for each comment.
- Providing an empty state when no comments exist.
- Providing inputs for author and body.
- Showing remaining-character or maximum-length guidance.
- Preventing submission when required values are invalid.
- Sending a create request and updating the displayed list after success.
- Showing loading, submission, validation, not-found, and server-error states.
- Preventing duplicate submissions while a request is pending.
- Escaping comment content and rendering it as plain text unless safe rich text is an explicit requirement.
- Adding delete or edit controls only if those operations are in scope and authorized.
- Deciding whether comments load with tasks or only when a task is opened.
- Preserving accessibility for labels, errors, focus handling, and keyboard interaction.

Do not assume whether this belongs on a task card, detail page, modal, drawer, or another interface until the actual frontend structure is reviewed.

## 5. Migration or Data-Shape Notes

The required work depends on the application’s storage model:

- For a relational database, introduce a comments table or equivalent entity with a task reference, constraints, and an index supporting task-based lookup.
- For a document store, decide between embedded comments and a separate collection.
- For in-memory or file-based storage, define the comment collection, task lookup, reset behavior, serialization, and deletion semantics.
- For existing persisted task records, avoid requiring a comments field unless the chosen representation needs one; if embedded, default missing comment collections safely.
- Define whether task responses embed comments, expose only a count, or require a separate request.
- Keep `created_at` in UTC and define its serialized format.
- Ensure UUIDs remain strings at API boundaries even if storage uses a native UUID type.
- Plan rollback and compatibility behavior if persistent production data exists.
- Consider indexing, pagination, or bounded loading if tasks may accumulate many comments.

No migration should be designed until the actual storage and deployment approach is known.

## 6. Open Questions

- Which comment operations are in scope: create and list only, or also retrieve, edit, and delete?
- Should `author` be free-form text or derived from an authenticated user?
- Are comments public to every task viewer?
- Who may edit or delete a comment?
- Should author and body values be trimmed before validation and storage?
- Is an all-whitespace body invalid?
- Should task deletion cascade to comments?
- What list ordering is required?
- Is pagination necessary?
- Should task responses include comments or a comment count?
- Can comments contain Markdown, links, mentions, or attachments, or only plain text?
- May an edited comment change its author?
- Are audit fields such as `updated_at` or `edited` needed?
- Are rate limiting, moderation, or abuse controls required?
- What error format and status-code conventions must the feature follow?
- What storage, route, testing, and frontend patterns already exist?

# Assumptions This Plan Makes

- Comments are subordinate to tasks and cannot exist without a valid task.
- The server generates comment IDs and timestamps.
- UUID strings are the public identifier format.
- Timestamps are serialized in an established UTC-compatible format such as ISO 8601.
- Creating and listing comments are the minimum useful operations.
- Comment bodies are plain text unless a richer format is explicitly selected.
- Validation occurs on the server even if the frontend also validates.
- The application has some established conventions for errors, routing, testing, and UI states that this feature should follow.
- Storage can represent a one-to-many task-to-comment relationship.
- Authentication, authorization, pagination, editing, and deletion requirements have not yet been decided.

# Parts Most Likely to Be Wrong After Reading a Real Repository

- The illustrative nested route structure and supported HTTP methods.
- Whether the application separates request and response models.
- Whether UUIDs are represented as strings or native UUID values internally.
- Whether comments should be stored separately or embedded in task records.
- Whether any migration is needed.
- The expected status codes and error response shapes.
- Whether unknown request fields are rejected.
- The project’s whitespace-trimming and string-validation conventions.
- How task deletion should affect comments.
- Whether authentication exists and whether `author` should be client-provided.
- Where comments belong in the frontend and how data fetching is organized.
- Whether the frontend has automated tests.
- The test framework, fixtures, storage reset strategy, and naming conventions.
- Whether list ordering, pagination, editing, or deletion are required.
